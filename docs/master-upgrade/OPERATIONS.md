## Access and operator responsibilities

The table describes Nortivo/Invest identity and trading access. On the daughter-company website, every public visitor starts a separate KORVNT guest session. KORVNT stores its enquiries, conversations, receipts, presence and indexes in independent namespaces with separate vault keys and encryption purpose. The same-origin public function has no route to portfolio, investment chat, staff login or administration. The dedicated KORVNT staff inbox remains on the parent company host. It requires both normal verified named-admin MFA and an additional current KORVNT operator UUID. Public availability is specific to that inbox. A visitor can revoke their KORVNT session on the device. A saved tracking proof continues to provide the case status. [Company-specific workflow contract](../WORKFLOWS.md)

| Actor | Actual authority and checks |
| --- | --- |
| Guest | A host-only, HttpOnly browser credential gives access to that guest’s conversations. The server stores a hash lookup and encrypted issuance/expiry. It enforces a 30-day lifetime. Tracking from a different browser requires a request reference and private tracking proof for an unclaimed guest request. |
| Verified customer | A live session resolves the current account on the server. The workflow requires verified email and an enabled account. Private reads and writes check ownership. Claiming a guest conversation requires possession of the guest credential and a matching verified email on any linked requests. After a claim the former guest loses access. |
| Owner | An active, verified server account with an operator-provenanced grant receives Pro entitlements and unlimited internal monthly AI allowance. Billing continues to report the actual subscription state. Ordinary customers retain their own plan and quotas. The retired provisioning endpoint is absent. |
| Named operator | A verified, enabled user with an approved UUID or persisted owner grant signs in with a password and enrolled TOTP or a one-use recovery code. Admin requests recheck current session, role and enrollment, and require admin MFA less than five minutes old. The admin session expires after eight hours. Signing in again refreshes proof. Mutations require matching origin and a session-bound CSRF token. |
| Broker-capable account | A current entitlement, current enrolled MFA and scoped step-up, connection ownership, consent and the applicable risk/release gates govern operations. Product step-up is limited to ten minutes. OAuth binding rechecks the original session before credential exchange and binding. An owner grant, provider quote or support request cannot transmit an order. |

Customer and operator credentials are host-bound. The core operator cookie is Secure, HttpOnly, SameSite Strict, uses path `/` and has no Domain attribute. The gateway forwards the synthetic store and local-only environment. The browser must reopen the proper origin when moving between company, Invest and Security. Before a future release, independently validate sign-in and current MFA on the intended hosted admin origin, approved UUIDs, deactivation and recovery, real TLS, and the platform’s trusted connection-address header. Keep ordinary accounts separate from administrator approval. ## Configuration, backup and response

For KORVNT, keep `KORVNT_SESSION_SECRET` and the `KORVNT_VAULT_KEYS` ring independent from Nortivo’s secrets. Select the active key with `KORVNT_VAULT_CURRENT`. Keep `KORVNT_OPERATOR_USER_IDS` minimal and review every dual-company grant. Include KORVNT-specific namespaces, original cryptographic contexts and hold/deletion decisions when backing up or retiring a case. The synthetic SQLite drill restores both companies’ encrypted conversations from one closed database snapshot using separately recoverable key rings. The real customer handlers can read their own restored data and deny cross-company reads or the wrong company key. Separate KORVNT isolation tests check guest revocation and operator grant loss. A hosted restore with both companies and separately recoverable keys remains a release gate. [KORVNT boundary tests](../../tests/workflow-korvnt.test.mjs)

1. Keep authentication, MFA, broker, workflow and provider credentials server-side with separate custody and an offline recovery procedure. The workflow ring uses `WORKFLOW_VAULT_KEYS`, a protected JSON map of key IDs to independent standard-base64 32-byte keys, and `WORKFLOW_VAULT_CURRENT`. MFA uses `PRODUCT_ENCRYPTION_KEY` in its existing base64url format. Broker tokens use the separate standard-base64 `PRODUCT_BROKER_TOKEN_KEY`. Preserve old values required by retained data. Public branding never triggers key rotation. [Configuration reference](../../.env.example)
2. For workflow-key rotation, add the new key to the ring and select it for new writes. Take a verified backup with separately recoverable keys. Reseal each existing workflow record under its original namespace, storage owner and key using a version-checked replacement. Re-read and retry version conflicts. Compare counts and perform a new-key-only restore before retiring an old key at the end of the backup and rollback horizon. Existing MFA and broker formats require their own reviewed migration or reconnect procedure. [Rotation procedure](../../services/security-core/docs/privacy-data.md)
3. The local recovery test restores a closed SQLite database to a separate directory. A verified Nortivo customer and a KORVNT guest read their own encrypted conversations with the matching vault keys. Cross-company reads, foreign and revoked sessions, and incorrect keys fail closed. A hosted restore still needs separate evidence for snapshots, permissions, recovered keys, complete data, time and recovery point. Proposed initial account/research targets are a 24-hour recovery point and an eight-hour recovery time. Financial workflows need independently agreed targets. [Restore test](../../tests/security-core-restore.test.mjs) · [Recovery procedure](../../services/security-core/docs/operations.md)
4. Review denied access, dependency errors, quota pressure and audit delivery when operating the service. The evaluator can identify ten denials or three unavailable events for a route in a five-minute export. The application produces sanitized events. A durable collector, scheduled evaluation, monitored destination and tested receipt still need an owner and hosted configuration. For an incident, Noah isolates the affected route, preserves minimal evidence under restricted access, revokes affected access, reconciles authoritative records and verifies restoration before reopening. [Signals and incident response](../../services/security-core/docs/operations.md)
5. Tighten permissions on approved hosted functions and migrations. Compare the existing namespace constraint, database grants, row security and atomic RPCs before any future schema application. Confirm live destinations and cost settings with the owner. Keep signup, host migration, customer feeds, external notifications and execution gated until their individual checks pass. After a rollback, preserve business records and idempotency receipts, keep earlier read keys available, and reconcile outstanding billing and broker state before resuming writes.
