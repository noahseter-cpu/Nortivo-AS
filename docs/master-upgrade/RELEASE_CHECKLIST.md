# Combined release and rollback checklist

**Prepared for the KORVNT.no combined review on 19 November 2026. No production release, migration, host activation or external delivery was executed as part of this assignment.** Noah must approve the exact combined revision and proposed external actions after reviewing the local result. Record the owner, date, evidence location and outcome for each applicable item in a private release log. Keep credentials, real account identifiers, customer records and signed deployment inputs out of public source, screenshots and review documents.

## 1. Establish the candidate and recovery point

- [ ] Identify the combined source revision or immutable candidate archive and digest, previous known-good application release, current host routing/configuration and last verified database backup. Preserve the original checkout and unrelated concurrent changes.
- [ ] Reconcile the previously published owner/feed baseline with the current KORVNT, admin, support, Invest, billing, OAuth, trading and portfolio source. The older isolated owner/feed handoff predates parts of this candidate. Its provisioning/deployment directions are historical. The consumed owner bootstrap endpoint must be absent.
- [ ] Record current Netlify build command, publish directory, bundled Functions, edge rules, environment scopes and deployed app IDs privately. Confirm the intended existing Netlify site and Supabase project. The review server, synthetic accounts, local fixture keys, SQLite files, operational logs and private workspaces belong outside the deploy artifact.
- [ ] List the person authorized to stop rollout, the private rollback procedure and the criteria for choosing that release. Keep a private export of the previous platform configuration, including the required reader key IDs. Limit access to the key-management system separately.

3. Release the combined candidate to the existing application hosting surface with static pages, assets, Functions and edge routing together. Keep protected production settings outside source. Keep KORVNT_SITE_READY and KORVNT_ALIAS_READY closed until their individual prerequisites are satisfied.

Unnecessary legacy subdomains do not need DNS or certificates. On nortivo.no, verify that /security/, /en/security/ and /nb/security/ continue to serve their own KORVNT introductions, framework information and explicit links to korvnt.no. Review bounded error rates and provider spend. Record the actual release ID, smoke evidence and unresolved items privately.

## Rollback and incident decision

| Trigger | Immediate action | Recovery verification |
| --- | --- | --- |
| Broken KORVNT hostname, TLS or alias | Close affected alias or canonical readiness, or restore the reviewed edge build. Revert only the DNS values changed for this release if required. Preserve the meaningful parent pages, receipts and encrypted KORVNT records. | Check Nortivo and Invest EN/NB routes, parent introductions, host isolation, certificates and eventual DNS convergence. A cached permanent www redirect may continue pointing to canonical, so maintain a safe apex response during recovery. |
| Account rights, MFA, cookie or billing regression | Stop accepting affected privileged mutations. Preserve session and event evidence. Restore the last reviewed artifact/configuration that enforces named MFA and ownership. Keep the protected path unavailable if an older release would reintroduce shared-password access. | Check the named operator, fresh MFA and logout/revocation, owner and ordinary account access, signed-event reconciliation and private response boundaries. Do not fix access by changing real account roles or weakening CSRF. |
| Chat, project or vault failure | Suspend new workflow traffic. Keep the DB, old and new reader key IDs and capture receipts. Revert the application entry to a reviewed compatible version. Retain the published references and pending customer follow-up list in restricted storage. | Restore to an isolated copy, open sample records with their original context, verify a tracked reference, pagination, retry/idempotency and operator read. Reopen traffic only after the owner approves recovery. |
| Unexpected external spend, provider exposure or trading activity | Disable the affected provider capability or worker through the approved emergency procedure. Keep authorized risk-reduction controls available. Preserve request and provider event IDs. | Reconcile the provider’s authoritative state, access scopes, usage and funding limits. Credential revocation/rotation, real orders and incident communications require the applicable incident authorization. |
| Database integrity or privacy incident | Stop affected writes, restrict access, preserve private evidence and invoke Noah’s incident process. Do not drop namespaces, delete receipts or restore over production as an automatic rollback. | Recover a separate verified copy, quantify changes after the backup, reconcile accepted requests and payment/provider events, and approve any production restore or customer communication separately. |

Release closeout requires recorded host behavior, per-provider state, administrator verification, data-recovery evidence, final test results and owner acceptance. A later production release does not establish certification, continuous monitoring or authorized live trading.
