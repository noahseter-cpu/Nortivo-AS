# KORVNT.no domain and application preparation

**Local review only.** The owner reports purchasing korvnt.no through Uniweb. This assignment has not changed the domain, its registrar, nameservers, email, HTTPS, hosting project or production configuration. Domain ownership alone does not establish a registered company name or trademark clearance.

## Pages and host boundaries

| Host | Intended role and route |
| --- | --- |
| korvnt.no | KORVNT’s independent customer-facing website. The edge serves its complete English or Norwegian page from the dedicated korvnt directory. The customer API accepts same-origin service enquiries, private tracking and KORVNT conversations. |
| www.korvnt.no | Prepared alias to the canonical apex. Supported English/Norwegian pages redirect to the corresponding language. The policy allowlists asset paths and language parameters and strips private query and fragment context. It denies unsupported paths, private operations and customer API calls on aliases. |
| nortivo.no | Parent company, research, guides and trading technology. /security/, /en/security/ and /nb/security/ retain substantive parent/daughter and integration information and link to korvnt.no. These pages remain on Nortivo. |
| invest.nortivo.no | Existing independent Invest platform and terminal. Its subscriptions, accounts, support and portfolio records retain their own access model. |
| security.nortivo.no and korvnt.nortivo.no | Optional compatibility host rules. Activation is discretionary and requires separately approved attachment, DNS, certificates and readiness. A new canonical launch does not require activating these hosts. |
| Local review | nortivo.localhost:4490, invest.localhost:4490 and security.localhost:4490 remain usable. korvnt.localhost:4490 is the local counterpart to korvnt.no. The compatibility preview hostname has its own browser cookie scope. Use one hostname throughout a guest journey. |

KORVNT uses a guest credential scoped to its own host, its own session secret, vault ring and storage namespaces. Staff use the private company-hosted inbox, first passing the existing current named-administrator and MFA checks and then an explicit KORVNT operator grant. This review implements no shared visitor login, cross-domain cookie, single sign-on or cross-domain callback. A KORVNT page has no access to the Invest account, holdings, billing, private Nortivo transcripts or dashboards. The asset allowlist contains the reviewed public frontend resources only. ## Instructions for a separately authorized activation

1. Identify the existing Netlify site that runs the combined Functions and edge router. Preserve its current main Nortivo hostname, Invest domain, build options and previous verified release. Treat KORVNT as a second application identity on the existing hosting surface. Review any platform-level primary-domain redirect before activation so Nortivo pages keep their own canonical addresses.
2. Identify the **authoritative DNS operator**. Uniweb’s account lists the domain’s registered nameservers. Uniweb’s DNS panel applies when its nameservers serve the zone. If the authoritative nameservers are external, change the zone there under the separate approval. Privately record current records and TTLs, access owners and restoration instructions. [Uniweb nameserver guidance](https://support.uniweb.no/hc/nb/articles/51181192852625-Hvordan-finner-jeg-ut-om-domenet-bruker-ekstern-DNS)
3. After approval, attach korvnt.no to the intended hosting site and check the corresponding www hostname. In Netlify’s production domain settings, open the domain-specific DNS verification details. Use the assigned values for the actual site and network tier. For the apex, use the provider-supported ALIAS, ANAME or flattened record if available, or the assigned A-record fallback. For www, use the assigned CNAME target. Record only the approved record names/types, before/after values and TTLs in the restricted change log. [Netlify external DNS](https://docs.netlify.com/manage/domains/configure-domains/configure-external-dns/)
4. Where Uniweb operates the DNS zone, locate the domain under Mine produkter, then Administrer domene and DNS. Compare the proposed entries with existing apex and www entries. Follow the DNS provider’s apex-name syntax and use its record editor for the individually approved changes. Preserve unrelated MX, SPF, DKIM, DMARC and verification records. Website activation requires no email service. [Uniweb record editor](https://support.uniweb.no/hc/nb/articles/45903543708433-Slik-oppretter-du-DNS-oppf%C3%B8ringer)
5. Verify actual public DNS answers from independent recursive resolvers. Netlify’s managed certificate process depends on working DNS and coverage of the assigned names. Verify the status in Domain management → HTTPS and check the certificate identity and HTTPS response for both canonical and www. Review restrictive CAA settings and pre-existing conflicting records if issuance fails. Existing Nortivo and Invest HTTPS must continue to work. [Netlify HTTPS and aliases](https://docs.netlify.com/manage/domains/secure-domains-with-https/https-ssl/) · [Netlify TLS troubleshooting](https://docs.netlify.com/manage/domains/troubleshooting/troubleshoot-ssl-and-https/)
6. Privately configure KORVNT_ORIGIN for the exact canonical HTTPS origin, a separate KORVNT_SESSION_SECRET, KORVNT_VAULT_KEYS and KORVNT_VAULT_CURRENT, and the explicitly authorized KORVNT_OPERATOR_USER_IDS. Rehearse the prepared namespace migration on an isolated PostgreSQL copy. Verify scoped access to captured requests and recovery of sealed records before opening real data collection. Keep the legacy parent pages and the Invest origin intact.
7. After the approved build, TLS and data prerequisites, set KORVNT_SITE_READY for the canonical site in the required edge and function environments. Verify English/Norwegian pages, artwork/fonts, canonical tags, exact-origin API, cookie isolation, customer retry, staff response, end session and private tracking. Check denial on both the edge and direct function entry points. Enable KORVNT_ALIAS_READY only when the intended alias routing is ready. Test www apex redirection, unsupported methods/paths and language preservation. The alias readiness flag also covers configured compatibility names: inventory attached hosts before enabling it. Keep optional aliases unassigned where unnecessary.
8. Keep the site’s development qualification. External delivery, a live reporting mailbox, monitoring, billing, SSO, cross-domain credentials and sensitive-evidence upload require their own operating decisions. The local initial form accepts service area, contact email and a brief summary. It must not accept evidence files or secrets.

## Rollback

If traffic resolves incorrectly, disable the affected alias or canonical routing under the agreed rollback procedure. Preserve the accepted requests, hash lookups, receipts and all reader keys. Revert only the hosting/domain records changed for this release, using the recorded previous targets and TTLs. Recheck both the public DNS answers and TLS for each affected hostname. Cached redirects can outlive a configuration change, so preserve a safe response on the canonical host during recovery. The meaningful parent pages remain available independent of KORVNT availability. Reopening the site requires evidence that both customer and named operator paths enforce the intended isolation.
