# Nortivo Invest conversations and KORVNT service enquiries

## Company boundaries

| | Nortivo and Invest | Standalone KORVNT |
| --- | --- | --- |
| Customer entry | The same-origin terminal function handles chat, bot and engine requests. A verified account can explicitly claim a guest conversation on that origin. | The same-origin `korvnt-service` function handles guest chat, five service-enquiry types, tracking and ending the guest session. It has no account login or account-claim path. |
| Guest credentials | Existing guest and terminal session formats continue to work. | A new host-only `__Host-korvnt_workflow` cookie uses a separate secret. The stored guest issuance also binds the issuing origin. A 30-day expiry or the visitor’s end-session action revokes its authority. |
| Private storage | Existing `workflow_threads`, `workflow_requests`, `workflow_index` and `workflow_receipts` retain Nortivo ownership and their original encryption context. | Corresponding `korvnt_*` namespaces use their own key ring and authenticated `korvnt.workflow.*` purpose. Server-selected namespaces partition reads, writes, listing, receipts, presence and tracking. |
| Staff | The company admin origin checks the named verified account, current enrollment, five-minute MFA freshness, revoked session and request CSRF token. | A separate `korvnt-inbox` function on the company origin requires those same checks **plus** a current UUID in `KORVNT_OPERATOR_USER_IDS`. Every request and online-lease lookup checks the current grant. This release supports explicitly dual-approved staff. An independent KORVNT-only staff role would require a further authorization and UI change. |

The initial enquiry accepts a service, email address and short plain-text summary. Visitors can ask about cybersecurity, website security, account security, website building/design or cybercrime asset-recovery assistance. Submission yields a durable KR reference and a private tracking proof. The proof reveals status and customer-visible follow-ups. The original guest session accesses the linked conversation. Use the company workspace for authorized replies and status changes. Ending a guest session clears that credential. A previously saved tracking proof has an independent lifetime. No claim, KYC, trading, wallet, evidence-upload, guaranteed recovery, purchase or external email flow follows submission.

The initial form rejects files and unexpected fields. Recognizable labeled credentials and key formats are rejected in KORVNT free text. Arbitrary prose still requires careful handling. A private evidence exchange would need verified authority, a purpose, recipient, consent, access limits, restricted storage and deletion. That exchange remains an operational prerequisite for collecting sensitive material. Keep transcripts, unverified allegations, wallet secrets and contact information out of audit logs.

Set `KORVNT_ORIGIN=https://korvnt.no` on the approved hosted release. The KORVNT root requires `KORVNT_SITE_READY`. Enabling `KORVNT_ALIAS_READY` separately permits allowed read-only aliases when DNS and certificates are verified. Existing parent introductions always remain at the Nortivo security paths. Local compatibility hosts issue independent host-bound guest sessions. Configure a new independent `KORVNT_SESSION_SECRET`, `KORVNT_VAULT_KEYS` and `KORVNT_VAULT_CURRENT`. The latter pair use the same format as the Nortivo vault and must contain separately generated keys. The server fails closed on missing or overlapping secret material. Existing untagged workflow records already belong to Nortivo. The additive schema admits the four additional namespaces without changing any existing row. An eventual transfer of a real case between businesses requires separately authorized, explicit export/re-encryption, access and retention decisions, customer communication where appropriate and a verified audit. There is no automatic migration or staff search across both companies. Retain each key ring through its data and backup retention period. A rollback can close KORVNT ingress while leaving Nortivo sessions and records intact.

Both businesses reuse the same server runtime, database adapter and existing service-role credential. The namespaces, authorization checks and cryptographic purpose separate application access. Database administrators still have access to storage metadata for both, and a privileged server with both vault rings can decrypt both sets of records. The existing per-owner resource ceiling spans the underlying product store. Review hosting/provider access, duty separation, data-controller responsibilities and recovery custody before admitting real case material.

## Local review

On the Invest homepage, send a message under Support. Open the launcher to read the same thread, then reload the page. The standalone Invest support page uses the same origin, session and history. The protected terminal uses its existing Support entry. The chat panel shows customer, human operator and system entries with server timestamps. A failed acknowledgment keeps the original message and request ID for retry. Participants can page through history in groups of 40. An operator can close or reopen a thread. A customer can start a new conversation after closure and revisit older conversations.

Choose a bot or engine, describe the goal, complete the conditional requirements, enter contact and project details, and review the brief. An undecided option is available for requirements, budget and timing. The review permits editing each stage. Submission asks Nortivo to assess scope. The record begins at **Received**. An operator can move it to **Under review**, **More information needed**, or **Closed** through the allowed transitions. Each follow-up includes a customer-visible note. The linked thread carries the same update. Budget and timeframe are the visitor’s indications.

A verified customer uses the verified email from their existing account. A guest receives a public reference and a private tracking key. Preserve both for later use. The original browser or verified account can track directly. A guest tracking key used from another browser permits viewing the project’s status and update notes. Private briefs and general support history require their own access checks. Claiming a guest conversation requires an explicit action, the unexpired original guest credential and a current verified account. The account email must match the contact on every project attached to the guest conversation. After linking, the guest credential and former tracking key lose access to the claimed records.

Drafts, pending sends and the latest submission acknowledgment use tab-scoped session storage with separate identity keys. This supports reloads in the same tab. Visitors who need a durable guest tracking key should save the submitted reference and private key before closing the tab. Draft access depends on access to that browser profile. The accepted brief and transcript live in the server store.

## Operators and availability

The company administration workspace has a **Conversations & projects** view. Operators sign in through the existing named account and current MFA flow. The inbox can list and page through both queues, inspect full briefs, reply, follow up, link a request to another conversation belonging to the same customer, and change supported states. Requests reach the inbox when the database transaction commits. In-app replies and follow-ups become visible when customers refresh or their visible chat polls. A field in the encrypted transaction receipt captures the notification event and recipient role. There is no external delivery worker in this workflow.

Support accepts asynchronous messages by default. An operator may explicitly choose **Be available for chat** in the protected inbox. Active, visible inboxes renew a 45-second lease every 15 seconds. Switching away stops renewal and requests removal of the lease. The public availability check revalidates the operator’s named role, live session, MFA enrollment and fresh administrative proof through the shared admin lookup. Identity and session hashes stay private. Clients bound the online label by the returned lease duration. A failed availability check has an unknown state. No typing, read receipts, AI agents or response-time estimates are simulated.

## Trust boundaries

| Data path | Control and evidence |
| --- | --- |
| Customer session | Same-origin `/.netlify/functions/terminal?action=workflow-session` reuses the existing terminal cookie path. Current account state, verification and ownership are read on the server. An invalid or revoked presented account session cannot silently become a guest. |
| Guest session | Opaque 32-byte server-issued random secret in an HttpOnly, Strict, host-only cookie. Production uses a Secure `__Host-` cookie with Path=/ and no Domain. SQLite or Supabase holds a hash-addressed, encrypted issuance record with a 30-day server-checked expiry. HTTP loopback uses an explicitly local cookie name. |
| Mutations and private reads | Exact-origin checks, CSRF bound to the live session, bounded JSON, field allowlists, per-field limits and server-derived authorship. Tracking proofs travel only in POST bodies. Responses have private no-store headers. The new workflow accepts text only and rejects attachments. File storage and malware scanning are outside this implementation. |
| Rate limiting | Shared atomic terminal rate store enforces 180 requests per connection/minute, 48 writes per connection/minute, 24 writes per subject/minute, 30 tracking attempts per connection/minute, and 40 new guest credentials per connection/hour. Operator controls also apply. A store outage returns a bounded failure. Adjust limits only against observed use and abuse. |
| Named operator and presence | Existing private admin cookie, fresh MFA, verified enabled account, server-granted privilege, origin and CSRF checks protect every inbox operation. The lease is encrypted. The public endpoint returns aggregate availability and remaining lease time only. |
| New private records | The KORVNT AES-256-GCM vault seals all four new namespaces, including transcripts, project briefs, email, identity binding, session issuance, presence, private follow-ups, receipts and stored response proofs. Associated data binds namespace purpose, immutable storage owner and record key. AES ciphertext is authenticated before plaintext reaches a response. Database metadata exposes namespace, record address, immutable owner ID, sequence, version, approximate size and access timing. |
| Guest claims and project links | Server-side checks verify the current credential and verified identity. The immutable storage owner remains part of the vault context after a claim. The sealed current ownership binding determines subsequent access. Public references alone never grant cross-browser access. |
| Transactions and recovery | Thread updates, sequence allocation, message rows, reference creation, idempotency receipts and notification capture commit together through `product_transact` or the existing SQLite transaction. Repeating the same ID and payload returns the original acknowledgment. A changed payload using that ID returns a conflict. |
| Audit and service dependencies | The existing allowlisted audit logger emits bounded route, decision, status, event ID and pseudonyms. Mutations require successful pre-action audit acceptance. Failed post-write acknowledgment is recoverable with the same request ID. Operational log delivery, monitoring and alert response depend on the hosting setup. |

The previous ticket/email system has separate tables, access links and delivery behavior. Existing tickets, historical email, project workspaces, portfolios, brokerage credentials, provider records and backups were not migrated to the conversation vault. Customers should leave secrets, passwords, seed phrases, API credentials and balances out of messages. Free text can contain information a customer chooses to type. The service does not diagnose or redact all sensitive text.

## Configuration and data operations

The shared terminal store uses its existing configuration and service-role access. New server-only configuration requires `WORKFLOW_VAULT_KEYS`, a JSON map of key IDs to canonical standard-base64 encodings of independently generated 32-byte secrets, and `WORKFLOW_VAULT_CURRENT`, the active key ID. Use the existing hosting secret manager for production. Store key backups and database backups under separate access controls. Neither browser bundles nor source control should carry key material. Missing configuration or unverifiable ciphertext produces a bounded unavailable response.

`supabase/workflows.sql` is prepared for review after `terminal.sql` and `product.sql`. It extends the installed namespace constraint with `workflow_threads`, `workflow_requests`, `workflow_index` and `workflow_receipts`. It preserves existing namespace rules and grants. Local tests use SQLite. No hosted SQL, production records or external notification destinations were contacted. Before rollout, validate the exact target constraint, service-role permissions, RLS and the installed RPC versions against a disposable PostgreSQL copy.

For key rotation, retain old readers, provision a new independently generated key, then switch the current write ID. Rewrap each record using its stored namespace, owner and key, with a version check. Resume conflicting records from current versions and verify counts and decryptability after a restore. The current release supplies the vault primitive and receipt/address design. A reviewed migration job, production key custody and post-rotation restore drill remain release work. Keep old keys until all required records and retained backups can be recovered under the agreed procedure.

A 30-day session expiry ends guest access. Request keys and server transcripts have independent lifetimes. Automatic deletion of customer transcripts, project requests, credentials after expiry, receipt acknowledgments and backups has not been implemented. Before collection from real users, the service owner must approve retention periods, assign an owner for deletion, and verify deletion across live data and backup expiry. An erasure inventory must traverse owned and claimed thread indexes, individual message rows, attached request records, guest issuance records and receipts, including records retaining the original storage owner. Retire tracking access when removing a request. Deletion and rewrap jobs should pause on version conflicts and be tested on restored copies first.

On a suspected disclosure, suspend affected access, revoke the relevant admin or product sessions and guest issuance records, preserve bounded audit evidence, identify affected key IDs and records, and follow the incident owner’s notification process. For rollback, stop routing new workflow traffic, retain encrypted records and all reader keys, and return visitors to the previous support entry while the owner decides how to process the outstanding queue. Dropping namespaces containing records is destructive and requires separate review. Existing email ticket handling and trading paths are independent of this rollback.
