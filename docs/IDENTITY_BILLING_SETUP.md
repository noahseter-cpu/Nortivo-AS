# Identity, storage and billing setup

This extends existing terminal users/sessions. It does not install Supabase Auth, assign old accounts a subscription, change UUIDs, merge guests or replace terminal state. `PRODUCT_ENABLED=false` retains the original handler. Product records use the same SQLite file locally and additive `public.product_records` in Supabase.

## Routes

All application actions stay at the terminal function. Secure/HttpOnly/SameSite=Strict cookies retain the exact function path. Same-origin and authenticated POST CSRF checks apply. Only GET product-broker-callback accepts a cross-site return after request-origin allowlisting; cryptographic one-use state is independently checked. Success redirects to the localized terminal. Clients cannot choose arbitrary provider customers or storage keys/owners.

- GET product-plans returns exact catalog, ready, per-plan availability, readiness and capabilities. GET product returns authenticated account snapshot/CSRF. GET session preserves the old snapshot plus product.
- POST signup accepts email,password,name?,tier?,interval?,locale?,returnPath?. New/existing addresses receive the same generic result; sign in after verification. Login requires email/password and code or recoveryCode when MFA enabled. Stored journey survives unless an explicit new tier is selected. Logout revokes the session.
- Public POST product-verify {token}, product-forgot {email}, product-reset {token,password}. Authenticated POST product-resend {}, product-change-password {currentPassword,password}; GET product-sessions; POST product-revoke {sessionId} or {all:true}. Existing native scrypt protects passwords. Recovery delivery failures retain the generic public result and produce safe diagnostics. Active sessions are capped at50.
- POST product-select-plan {tier,interval,locale,returnPath} persists allowlisted intent. Verification returns locale/selectedPlan/returnPath. Server prices and safe paths determine Checkout returns.
- POST product-mfa-enroll {password} returns setup URI/seed; product-mfa-confirm {code} enables it and displays eight single-use recovery codes once. OTPAuth9.6.0 provides TOTP; AES-256-GCM encrypts actor-bound seeds. Counters reject replay. product-mfa-stepup {code|recoveryCode,scope:broker|execution|security} creates ten-minute session proof. Execution includes broker actions; security covers sensitive scopes. product-mfa-disable {password,code|recoveryCode} revokes sessions. Losing authenticator and recovery codes requires manual support; no insecure bypass exists.
- POST product-checkout {requestId,tier,interval} and product-portal {requestId} return hosted URLs. One customer mapping binds existing actor/mode. Tabs reuse open Checkout. Signup/purchase never starts trading.
- POST product-change-preview {tier,interval} returns previewId/charge/effective date. product-change {requestId,tier,interval,previewId} replaces one item. Portfolio-to-Pro uses pending_if_incomplete/always_invoice; failed payment retains paid Portfolio. Pending authentication returns hosted paymentUrl. Other changes schedule at actual renewal. Durable per-receipt progress resumes lost responses with original Stripe idempotency keys.
- POST product-cancel/product-resume {requestId} changes renewal. Cancellation releases an owned pending schedule before setting current-period-end cancellation. product-refresh {requestId} reconciles missed events. Each new refresh needs a newID; retries retain the originalID/result.
- POST product-deletion-request {requestId} audits support review and reports billing/broker consequences. New risk entries stop; history/export/cancel/stop/reduce remain. Support resolves recurring billing, broker access and retention before destructive disposition; no automatic delete leaves orphan charges.

Entitlements require verified identity and provider-confirmed paidUntil. Past-due never invents grace. Purchased access lasts its legitimate period; expiry preserves account/billing, history/export and brokerage safety. Enabled public sample replay is backend read-only.

## Storage, operations and rollback

The server-only product store exposes get/list/transact. Omitting list owner exists only for internal worker/admin enumeration. SQLite IMMEDIATE transactions and sorted PostgreSQL owner/key advisory locks commit CAS together. Immutable ownership and versioned tombstones prevent reassignment and ABA. History/permanent receipts are never evicted for space.

Limits:32 changes/transaction;4MB transaction;2MB portfolio;250KB other record;50,000 records/100MB per owner;1,000 rows/list. Writes stop at limits while reads/export remain. Future expired-ephemeral cleanup must preserve financial receipts and worker fencing.

productIdentity atomically creates user/account, consumes verification or updates password plus revokes sessions. productCreateSession bounds sessions atomically. Local preview shares SQLite and does not load .env. Use the preview's --product flag; programmatic productEnv can supply explicit test/server configuration. Fixture email/Stripe adapters require explicit injection and PRODUCT_TEST_MODE true; no production fake subscriber/mail path exists.

Monitor webhook failures, pending receipts/schedules, paidUntil expiry, price configuration, email failures and service health. Reconcile using a fresh request after recovery. Multiple subscriptions require merchant review, never overlapping entitlements or silent refunds/cancellation.

Rollback: disable PRODUCT_ENABLED, redeploy the prior build and retain all data/Stripe records. Resolve customer billing/broker consequences deliberately. Do not drop product tables, erase receipts or liquidate accounts. Backup restoration is a separate reviewed recovery operation.
